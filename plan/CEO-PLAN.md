## Pre-review system audit

- **Prior review cycles.** 21 historical attempts sit in v2's `.engine/evidence/forward/attempts/`. The same areas were reworked repeatedly: routing, visual verification and receipts. That points to an architectural smell: the receipts and hash locks grew faster than the product.
- **UI scope.** Yes. Every artifact is a user-facing page, image or video, so Section 11 applies.
- **Taste calibration.** These are worth keeping:
  - v2's consent-first learner state with an FSRS scheduler (`.engine/scripts/praxteach/`);
  - its deterministic Markdown renderer with source-hash provenance;
  - the proof builds' "every number comes from `facts.json` captured from real compilers, plus a tamper test" (`proof/still-interactive/build.sh`, `check/assert_all.py`).

  These are the anti-patterns to avoid repeating:
  - keyword-regex routers (`routing.py:49-55`, `:105-108`);
  - receipts that pin hashes of files the tool itself rewrote (`configure.py`);
  - historical attempts shipped inside the install.
- **Landscape.** Report 05 already covers it, with 76 sources checked today. **Layer 1:** Manim and HyperFrames-style HTML video; Anki for spaced repetition. **Layer 2:** agent-first video tools (HyperFrames 0.8.x with local Kokoro TTS and `transcribe`), and in-page composition players. **Layer 3, the eureka:** every serious explainer pipeline treats the *render* as the product. For a tutor the product is the *verified lesson model*, and renders are cheap projections of it. One model with facts, claims, a trace and a storyboard fixes correctness, consistency across artifacts, and interactive video, all at once. Interactive video stops being a special feature: it is the video and the explorer projected from the same state timeline.

## Step 0

### 0A. Premise challenge

1. **Is this the right problem?**
   - The literal problem, "make v2 produce six artifact types well", is right but framed too low.
   - The real problem is that v2 has no single source of truth. It verifies files, not facts, and it routes by keywords, not by intent and the workspace's own contract.
   - So patching v2 means 114 local fixes. Restructuring around a lesson model removes whole classes of them.
2. **The actual outcome.** Prax learns C, then C++, DSA and GATE CS from explanations that are never wrong and look world-class, in the medium he asks for, inside his own study loop: a prediction first, the attempt log, spaced review.
3. **If we do nothing.**
   - v2 keeps routing "narrated video" requests to text-only answers.
   - It can't hold a video.
   - It ships wrong figures with "passed" receipts.
   - It also contradicts the workspace's Socratic contract.

   That is real pain, observed today, not hypothetical.
4. **Raised once and recorded, not re-argued.** `MISSION.md` in the C workspace warns against replacing practice with an expanding curriculum or dashboard, and that workspace has zero practice sessions logged. This plan is tooling. Prax chose to keep improving tooling, and this plan honours that choice in two ways:
   - **Build requirement:** the tool must make practice easier, not replace it. Prediction-first mode, cards wired to his spaced review, and exam drills are all in scope.
   - **Dogfooding requirement:** both exemplar lessons are C topics he needs anyway.

## Section 1: Architecture

```
                         +------------------------- ptk (Python CLI) --------------------------+
  request ──▶ route ──▶ | mode+medium+workspace contract ──▶ lesson.json (model)               |
  (agent)               |                                    │  facts  claims  trace  storyboard |
                        |   capture/c_runner ── clang,gcc-16 ┘                                   |
                        |                                    ▼                                   |
                        |  projectors: still │ explorer │ qa │ cards │ video │ ivideo          |
                        |        │               │                    │         │               |
                        |        ▼               ▼                    ▼         ▼               |
                        |   SVG/PNG         HTML (self-contained)   HyperFrames  player page    |
                        |                                           +Kokoro TTS  +state bridge  |
                        |  gates: values · tamper · claims · contrast · screenshots · media     |
                        |                     ▼                                                  |
                        |            build-report.json (passed | failed | not-run)             |
                        +-----------------------------------------------------------------------+
  ported from v2: render_markdown (Node) · praxteach state+FSRS (optional) · tool registry (fixed)
  external: clang · gcc-16 · node · playwright · hyperframes · kokoro venv · ffmpeg/ffprobe · manim (route only)
```

**Data flow and shadow paths (capture → model):**
- **Happy path:** compile with both compilers, run twice, the outputs match, and they're stored as facts with sha256 hashes.
- **Missing input** (no source or program for a fact): `ModelError("fact X has no source")`. The build stops.
- **Empty stdout:** stored as an empty-string fact. Allowed, but a value gate that expects text fails loudly.
- **Upstream error:**
  - a compile error gives `CompileError` with the compiler's stderr;
  - a timeout gives `RunTimeout`;
  - outputs that differ between compilers give `CompilerDisagreement`, which is valid when the behaviour is implementation-defined, but then a claim must say so;
  - outputs that differ between runs give `NondeterministicOutput`.

**State machine (lesson build):**

```
  draft ──capture──▶ captured ──project──▶ projected ──verify──▶ verified ──package──▶ packaged
    ▲                   │ fail                │ fail                │ any gate failed
    └──── edit ◀────────┴─────────────────────┴─────────────────────┘ (stays failed; never "verified")
  Invalid: projected→packaged without verify (ptk refuses); verified with a not-run gate marked passed (schema forbids).
```

**Coupling.**
- Projectors depend only on `lesson.json` and the style tokens.
- Gates depend on `lesson.json` and the artifacts, never on how a projector works internally.
- The C repo isn't a dependency; the capture runner is self-contained.

**Scaling.** A build costs one TTS pass per scene (cached) and one HyperFrames render, about 2–4 minutes for 60–90 s of video. Ten lessons in a pack cost about 30 minutes. The first thing to break at 10x is TTS and render time, so a content-hash cache and `--only` flags per projector handle it.

**Single points of failure.**
- The HyperFrames CLI, which auto-upgrades: the version is recorded in the report, and a `ptk host check` warns on drift.
- The Kokoro venv: falls back to macOS `say`, disclosed in the report.
- Playwright: if it's missing, the visual gate reports `not-run`.

**Security architecture.** No network endpoints. The capture runner executes C that the agent wrote, so it gets a temp dir, rlimits, a timeout, process-group kill and no network (`sandbox-exec` profile where available, with the absence disclosed). Explorer and IVE HTML are self-contained, with a CSP meta tag that blocks all remote fetches.

**Production failures per integration.**

| Integration | Failure | Handled by |
|---|---|---|
| HyperFrames | Upgrades mid-build and changes lint rules | Version pin warning |
| Kokoro | Long-path bug in its pronunciation data (seen today) | Venv setup applies the proven fix |
| Playwright | Browser cache purged by an outside cleaner (seen on 2026-10-08) | `PLAYWRIGHT_BROWSERS_PATH` set to the package's own state dir |

**Rollback.** v2.1 installs alongside v2 under a candidate name. Acceptance flips the `prax-teach-v2` symlink, and rollback flips it back: one command, about 1 second.

**Beautiful version.** One file, the lesson model, is the only thing an author writes. Everything else is a pure function of it, plus captured runs. A new engineer reads `lesson.schema.json` and the six projector files and understands the whole system.

**Platform potential.** Topic packs (Phase 2), a cpx integration that cards and drills feed into, and other learners' workspaces.

- **D6.1** Per-scene HyperFrames sub-compositions. *Accepted*, completeness 10 versus 7 for one file, because it fixes the proof's lint warnings.
- **D6.2** The capture runner is self-contained rather than importing cpx. *Accepted*: separate products and no cross-repo coupling.

  ModelSchemaError/RefErr  | Y        | stop; JSON pointer to the bad field            | "/facts/3/source missing"

**D7.1.** `GateNotRun` never counts as passed, and a build with any not-run gate is reported `incomplete`, not `verified`. *Accepted*, completeness 10. This is the direct fix for the v2 habit of passing on presence.

## Section 5: Code quality

- Keep one formatter for values, shared by all projectors, so the same fact can't render differently in two artifacts. That is DRY at the point that matters.
- No framework: templates are string templates with escaping. Over-engineering check: no plugin system for projectors in v2.1, since six fixed modules are enough.
- Branching budget: the router must not exceed 5 branches per function. Use a table-driven classifier with explicit rules plus tests, not regexes scattered through the code.
- **D10.1.** Table-driven router plus a dev prompt set of at least 60 prompts, kept separate from the holdout. *Accepted.*

## Section 7: Performance

- **Slowest paths.** Video render takes about 60–180 s, TTS about 1–2 s per sentence (cached), and Playwright screenshots about 5–10 s per artifact.
- **Memory.** Kokoro needs about 1 GB resident and HyperFrames' Chrome about 1 GB. With 24 GB RAM that's fine; renders still run one at a time.
- **Cache.** TTS by content hash, captures by source hash plus compiler version.
- No issues beyond caching. **D12.1.** Caching *accepted.*

## Section 8: Observability

- `build-report.json` per lesson records every gate with status, measured values, thresholds, tool versions, durations and artifact paths. `ptk report` prints it as a table.
- Logs are structured JSON lines to `build/<lesson>/log.jsonl`. They record the start and end of each stage with its inputs and hashes.
- Three weeks after a build, the report plus the logs reconstruct exactly what ran and which tool versions ran it.
- The "joy to operate" version: `ptk report --html` renders the build report with thumbnails of every artifact and gate.
- **D13.1** *Accepted.*

## Section 9: Deployment and rollout

1. Build and test in the candidate repo.
2. Install side by side into `~/.agents/skill-library/prax-teach-v2.1/` and link it under `prax-teach-v2.1-candidate` with `disable-model-invocation: true`, so it is reachable by direct call only.
3. Run the acceptance step: the holdout, both exemplar builds and the protected checks.
4. Once accepted, point `~/.agents/skills/prax-teach-v2` at v2.1 and remove the candidate link.
5. Rollback is to point the link back at the clean v2 install.

There is no migration of learner state, because v2.1 reads v2's `.prax-teach` format unchanged. The ported engine is the same code.

**D14.1** *Accepted.* The infrastructure that makes this routine: `ptk package --install` performs steps 2 and 4 with a dry-run diff first.
