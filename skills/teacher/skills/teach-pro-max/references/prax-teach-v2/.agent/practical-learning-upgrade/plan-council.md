## Round 1: Aristotle

**Restatement:** Decide whether practical executable learning belongs inside Teach Pro Max’s existing protocol, routing, and evaluation structure or warrants a separate subsystem, while reconciling the Python-ML lab without corrupting the dirty canonical candidate or bypassing exact-byte release gates.

**Alternative framing:** This is not a subsystem-design decision but a classification-and-promotion problem: establish practical learning as one teaching mode, treat the lab as its proving fixture, and separately control when verified candidate bytes become a release.

**Position:** Extend the existing seams. Practical learning is a delivery mode inside adaptive teaching. Put its sequence and evidence boundary in the teaching protocol, exercise them through existing evaluation machinery, keep visual routing in the current router, remove the lab’s unconsumed scene abstraction, and require authoritative-model reuse or literal-vector parity. Treat dirty visual-unification bytes as the candidate and promote only after fresh exact-byte receipts.

## Round 1: Feynman

**Restatement:** Decide whether practical executable learning belongs inside Teach Pro Max’s existing protocol, router, and evaluation seams while simplifying the Python-ML lab, without corrupting the dirty canonical candidate or bypassing exact-byte release gates.

**Alternative framing:** This is not a subsystem-design problem; it is a consistency repair between one teaching policy and one concrete lab that exposes missing policy coverage.

**Position:** Extend the existing seams. A new subsystem duplicates authority without a distinct runtime, owner, or invocation. Remove `scene.json` because it has no playback or synchronized consumer. Keep Python authoritative and permit JavaScript only behind literal parity vectors. Harden native HTML/SVG. Preserve the candidate’s dirty visual-unification work and never rewrite historical receipts or partially copy embedded files into the installed distribution.

## Chairman verdict

### Acceptable compromises

- The practical loop is a protocol branch, not a separately versioned subsystem.
- The Python-ML lab remains a concrete probe rather than becoming a reusable package template.
- Cross-runtime parity uses a small literal-vector seam rather than Pyodide.

### Kill criteria

- If implementation requires a second teaching invocation, the plan is invalidated and must return to the single-skill boundary.
- If scene/trace state gains no concrete playback or synchronized consumer, any scene abstraction must be removed.
- If exact-byte full verification or fresh review receipts fail, installed-distribution promotion is invalidated and remains parked.

### Concrete next step

Write failing public-seam tests for the practical protocol and the lab visual before changing production behavior.

### Unresolved questions

- GitHub issue publication awaits explicit approval for sending the full internal spec payload.
- Installed distribution promotion depends on fresh release evidence for all pre-existing dirty candidate work, not only this feature.

### Key agreements

- Reuse the protocol, router, evaluation, renderer, and distribution seams.
- Remove speculative scene infrastructure.
- Keep Python authoritative and require parity evidence.
- Preserve dirty candidate work and bind promotion to fresh exact bytes.

### Key disagreements

None material.

1. **Selected:** extend existing seams and reconcile the lab.
2. Create a new practical subsystem; rejected because it duplicates authority and state.
3. Keep the lab prototype unchanged; rejected because its claims and accessibility paths contradict the teaching contract.
